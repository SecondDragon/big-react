浏览器原生事件流

当你在浏览器中 点击一个按钮 时，浏览器并不是只触发这个按钮的事件处理函数。事实上，这个 click 事件会沿着 DOM 树传递三次。DOM Level 2 Events 规范定义了这三个阶段：

1.1 三个阶段

阶段英文名方向触发顺序
捕获阶段 Capture Phase 从根向下 ↓ Window → document → html → body → div → button
目标阶段 Target Phase 停驻 到达 button（实际点击的元素）
冒泡阶段 Bubble Phase 从子向上 ↑ button → div → body → html → document → Window
🔑 关键记忆法："先捕获，后冒泡"。事件先沿着 DOM 树从祖先走向目标（捕获），命中目标后再从目标走回祖先（冒泡）。大多数日常使用的 onClick 都是在冒泡阶段触发的。

1.2 动手验证

以下代码可以直接在浏览器控制台运行，直观感受事件的三个阶段：

// HTML 结构（在页面中准备）
// <div id="parent">
//   <button id="child">点我</button>
// </div>

const parent = document.getElementById('parent');
const child = document.getElementById('child');

// 捕获阶段监听（第三个参数为 true）
parent.addEventListener('click', () => {
  console.log('🔴 父元素 捕获阶段');
}, true);

// 目标阶段（child 上的监听）
child.addEventListener('click', () => {
  console.log('🟡 目标元素');
});

// 冒泡阶段监听（第三个参数为 false 或省略）
parent.addEventListener('click', () => {
  console.log('🟢 父元素 冒泡阶段');
}, false);

// 点击 button 后输出：
// 🔴 父元素 捕获阶段
// 🟡 目标元素
// 🟢 父元素 冒泡阶段
⚠️ 注意：目标阶段比较特殊——在目标元素（button）上注册的 addEventListener，无论第三个参数是 true 还是 false，都会按照注册先后顺序触发。因为此时事件已经"到达"了目标，不存在"先经过还是后经过"的问题。

1.3 捕获阶段实战场景（addEventListener 第三个参数为 true）

捕获阶段虽然日常用得少，但在以下三个场景中不可替代。核心原因是： 捕获阶段发生在目标元素收到事件之前，所以你可以做"拦截"或"预处理"。

场景一：全局埋点 / 用户行为分析

需求：你需要在用户点击页面上任意元素时记录点击位置和文本，但你不希望修改任何现有业务代码。

// 在 document 的捕获阶段统一收集所有点击
document.addEventListener('click', (e) => {
  const target = e.target;
  analytics.send({
    type: 'click',
    tag: target.tagName,
    text: target.textContent?.slice(0, 50),
    position: { x: e.clientX, y: e.clientY },
    timestamp: Date.now()
  });
}, true); // ← 关键：捕获阶段

// 为什么必须用捕获？
// 1. 某些业务代码里的 onClick 可能调用了 stopPropagation()
//    如果埋点在冒泡阶段，stopPropagation 会阻止埋点执行
//    但捕获阶段在 stopPropagation 之前，保证一定能收到！
//
// 2. 某些元素（如 video、iframe）可能阻止了冒泡
//    捕获阶段不受影响
🎯 核心要点：埋点一定要在捕获阶段做。因为业务代码随时可能调用 stopPropagation() 阻止冒泡，你无法控制第三方代码。捕获阶段是事件流的最上游，没有任何人能阻止你。

场景二：全局权限拦截 / 按钮禁用控制

需求：用户未登录时，阻止所有"需要登录"的按钮操作，且不影响按钮 hover 等其他交互。

// HTML 结构
// <form id="orderForm">
//   <button class="need-auth">立即购买</button>
//   <button class="need-auth">加入购物车</button>
//   <button>查看详情（不需要登录）</button>
// </form>

const orderForm = document.getElementById('orderForm');

// 在表单的捕获阶段统一拦截
orderForm.addEventListener('click', (e) => {
  const btn = e.target.closest('.need-auth');
  if (btn && !userStore.isLoggedIn) {
    e.stopPropagation();      // 阻止冒泡 → 按钮自己的 onClick 不会执行
    e.preventDefault();       // 阻止默认行为
    showLoginModal();         // 弹出登录框
  }
}, true); // ← 捕获阶段

// 为什么必须在捕获阶段？
// 如果用冒泡阶段：按钮自己的 onClick 已经先执行了！
// 你弹了登录框，但购买请求已经发出去了。
//
// 捕获阶段：表单上的监听器先触发 → 检查权限 → 不通过则 stopPropagation
// → 按钮自己的 onClick 被跳过了 → 完美拦截

场景三：拖拽时"抢走"子元素的点击事件

需求：实现一个拖拽排序列表，用户可能点击列表项的拖拽手柄开始拖拽，也可能只是点击列表项本身做其他操作。你需要在最外层容器上统一处理 mousedown。

// 拖拽列表容器
const list = document.getElementById('sortable-list');

list.addEventListener('mousedown', (e) => {
  const handle = e.target.closest('.drag-handle');
  if (handle) {
    // 用户在拖拽手柄上按下了鼠标 → 开始拖拽
    startDrag(handle.parentElement);
  }
  // 不是拖拽手柄？什么都不做，让子元素自己的 click 正常触发
}, true); // ← 捕获阶段

// 为什么必须用捕获？
// 子元素可能有自己的 mousedown 处理器
// 捕获阶段保证容器先感知到 mousedown，决定是否"抢走"事件
// 如果是拖拽手柄 → 容器接管后续的 mousemove/mouseup
// 如果不是 → 事件正常冒泡，子元素的 click 照常执行

1.4 冒泡阶段实战场景（addEventListener 第三个参数为 false / 默认）

冒泡阶段是你日常使用最多的模式，也是默认值。它的核心优势在于事件委托——把多个子元素的监听器合并到父元素上。

场景一：动态列表（事件委托的经典应用）

需求：一个 Todo 列表，用户可以添加/删除项。新添加的项也应该能响应点击删除。你不会想每新增一项就去绑定一次事件。

<ul id="todo-list">
  <li>买牛奶 <button class="delete-btn">×</button></li>
  <li>写代码 <button class="delete-btn">×</button></li>
  <li>健身   <button class="delete-btn">×</button></li>
</ul>

// ❌ 错误做法：每次新增都要手动绑事件
function addTodo(text) {
  const li = document.createElement('li');
  li.innerHTML = `${text} <button class="delete-btn">×</button>`;
  // 每次都得手动给新 button 绑事件！
  li.querySelector('.delete-btn').addEventListener('click', deleteItem);
  list.appendChild(li);
}

// ✅ 事件委托：只在 ul 上绑定一次，利用冒泡
document.getElementById('todo-list')
  .addEventListener('click', (e) => {
    if (e.target.classList.contains('delete-btn')) {
      const li = e.target.closest('li');
      li.remove();          // 移除列表项
    }
    // 点击的是 li 本身而不是删除按钮？编辑它
    else if (e.target.tagName === 'LI') {
      e.target.contentEditable = true;
      e.target.focus();
    }
  });
// 之后任意时刻 addTodo()，新 button 不需要额外绑事件！
// 因为点击会自然冒泡到 ul，被这个监听器捕获
💡 为什么这是"经典应用"？
这个例子体现了事件委托的全部优势：1 个监听器管理无数动态子元素。这也是你的 SyntheticEvent.ts 中 initEvent 在容器上只绑定一次的根本原因。

场景二：表单字段统一验证 / 数据收集

需求：一个复杂表单有 20+ 个输入框，你需要监听所有 input 的 blur 事件做校验，并在表单级统一收集数据。

<form id="profile-form">
  <input name="username" />
  <input name="email" />
  <input name="phone" />
  <select name="city">...</select>
  <textarea name="bio"></textarea>
  <!-- 更多字段... -->
</form>

const form = document.getElementById('profile-form');

// ❌ 不好的做法：给每个字段单独绑定
form.querySelectorAll('input, select, textarea').forEach(el => {
  el.addEventListener('blur', validateField);
  // 20 个字段 → 20 个监听器
});

// ✅ 事件委托：利用 blur 事件会冒泡的特性
// 注意：原生 blur 不冒泡！要用 focusout 代替
form.addEventListener('focusout', (e) => {
  const field = e.target;
  if (field.name) {         // 有 name 属性的才是表单字段
    validateField(field);   // 统一校验
    formData[field.name] = field.value;  // 统一收集
    console.log(`${field.name} 校验通过:`, field.value);
  }
});

// 后续动态新增的字段（比如"添加更多收货地址"）也自动获得校验

需求：一个 1000 行的数据表格，每行有编辑、删除、查看详情三个按钮。如果用传统方式，你需要绑定 3000 个事件监听器。

1.5 捕获 vs 冒泡：什么时候用哪个？

场景用捕获 (true)用冒泡 (false)原因
全局埋点 / 行为分析 ✅ ❌ 业务代码的 stopPropagation 会阻止冒泡埋点
权限拦截 / 登录检测 ✅ ❌ 必须在子元素自己的事件之前拦截
拖拽（容器接管子元素事件） ✅ ❌ 容器需要"抢先"判断是否接管
事件委托（动态列表等） ❌ ✅ 利用冒泡自然汇聚到父元素
表单统一校验 / 数据收集 ❌ ✅ 利用 focusout / blur 冒泡到 form
普通按钮点击 ❌ ✅ 日常默认行为，99% 的情况
大数据表格行操作 ❌ ✅ 事件委托减少内存占用（N 倍）
🤔 和你的 SyntheticEvent.ts 有什么关系？
你在 SyntheticEvent.ts 中 initEvent 用的是直接在容器上 addEventListener，第三个参数为默认的 false（冒泡阶段）。然后 React 自己模拟捕获和冒泡顺序——这就是 collectPaths 里 unshift vs push 的意义所在。React 只在容器上绑一次冒泡监听，然后自己沿着 Fiber 树去收集回调并决定执行顺序。

addEventListener 第三个参数完整速查

addEventListener 的第三个参数决定了监听器在哪个阶段触发，以及更多行为控制：

写法语义触发时机适用场景
false（默认）冒泡阶段事件从目标向上冒泡时事件委托、日常开发
true捕获阶段事件从根向下捕获时埋点、权限拦截、拖拽接管
{ capture: false }对象形式-冒泡同 false需要搭配其他选项时
{ capture: true }对象形式-捕获同 true同上
{ once: true }只触发一次首次触发后自动移除初始化、一次性引导
{ passive: true }被动模式不调用 preventDefaultscroll/touch 性能优化
 
// 以下三种写法等价
el.addEventListener('click', handler, false);
el.addEventListener('click', handler, { capture: false });
el.addEventListener('click', handler);  // 默认 false

// 以下两种写法等价
el.addEventListener('click', handler, true);
el.addEventListener('click', handler, { capture: true });

// 组合使用：只在捕获阶段触发一次
el.addEventListener('click', handler, { capture: true, once: true });

// 滚动性能优化：告诉浏览器不会阻止默认滚动
el.addEventListener('scroll', handler, { passive: true });

面试高频：stopPropagation 与 stopImmediatePropagation

这两个方法在面试中的考察频率很高，因为它们能精准测试候选人对事件模型的掌握程度。

event.stopPropagation()

阻止事件继续传播到下一层 DOM 节点。
同层下一个监听器仍会执行。

el.addEventListener('click', (e) => {
  e.stopPropagation();
  // 父节点收不到这个事件了
  // 但 el 上排在我后面的监听器还是会跑
});

event.stopImmediatePropagation()

阻止事件继续传播 + 阻止同一个元素上排在后面的监听器。

el.addEventListener('click', (e) => {
  e.stopImmediatePropagation();
  // 1. 父节点收不到了
  // 2. el 上排我后面的监听器也跳过了
});
🎯 必会面试题：一个元素上绑了 3 个 click 监听 A、B、C，A 中调了 stopImmediatePropagation()。问 B 和 C 以及父元素是否会收到事件？
答：B 和 C 不会（同一元素上后面的都被阻止），父元素也不会（冒泡被阻止）。 
// 经典面试题运行验证
child.addEventListener('click', () => console.log('A'), false);
child.addEventListener('click', (e) => {
  console.log('B — 调用了 stopPropagation');
  e.stopPropagation();
}, false);
child.addEventListener('click', () => console.log('C'), false);

parent.addEventListener('click', () => console.log('parent 冒泡'), false);

// 输出：A → B → C（注意 C 仍然执行了！）
// parent 冒泡 → 不执行（被阻止了）
//
// 如果把 stopPropagation 换成 stopImmediatePropagation：
// 输出：A → B（C 也被跳过了）

事件委托（Event Delegation）

事件委托是利用事件冒泡实现的经典设计模式。它的核心思想是：不在每个子元素上绑定事件，而是只在父元素上绑定一次，通过 event.target 判断实际点击的是哪个子元素。

// ❌ 不好的做法：给每个 li 都绑事件
document.querySelectorAll('li').forEach(li => {
  li.addEventListener('click', handleClick);
});

// ✅ 事件委托：只在 ul 上绑定一次
document.querySelector('ul').addEventListener('click', (e) => {
  if (e.target.tagName === 'LI') {
    console.log('点击了：', e.target.textContent);
    // 即使后续动态新增的 li，也会自动被这个监听器捕获！
  }
});
💡 事件委托的三大优势：
  1. 内存节约：10000 个元素只需要 1 个监听器
  2. 动态元素支持：后续新增的子元素自动获得事件支持
  3. 代码简洁：不需要在挂载/卸载时管理监听器

big-react 的合成事件系统

现在，我们把原生事件模型和你在 SyntheticEvent.ts 中的实现逐行对照。

5.1 整体架构

sequenceDiagram
    participant User as 用户点击按钮
    participant Browser as 浏览器
    participant Init as initEvent 容器监听器
    participant Dispatch as dispatchEvent 分发入口
    participant Collect as collectPaths 收集路径
    participant Flow as triggerEventFlow 执行回调

    User->>Browser: 点击 button
    Browser->>Init: 冒泡到 container，触发原生事件
    Init->>Dispatch: 构造合成事件，调用 collectPaths
    Dispatch->>Collect: 从 target 向上遍历到 container
    Collect-->>Dispatch: 返回 capture 和 bubble 回调数组
    Dispatch->>Flow: 遍历 capture 数组
    Flow->>Flow: 用 scheduler 优先级调度执行
    Dispatch->>Flow: 检查 __stopPropagation
    Flow->>Flow: 遍历 bubble 数组

5.2 事件委托的实现

你的代码中的事件委托，对应关系如下：

原生概念你的代码文件位置
在容器上绑定事件 container.addEventListener(eventType, ...) SyntheticEvent.ts:41
从 target 向上收集回调 collectPaths(targetElement, container, eventType) SyntheticEvent.ts:107
React 的 Props 存储 node[elementPropsKey] = props（存在 __props 上） SyntheticEvent.ts:29
事件类型映射 click → ['onClickCapture', 'onClick'] SyntheticEvent.ts:99

看一下核心的 collectPaths 方法：

function collectPaths(
  targetElement: DOMElement,
  container: Container,
  eventType: string
) {
  const paths: Paths = { capture: [], bubble: [] };

  while (targetElement && targetElement !== container) {
    // 从 DOM 元素的 __props 上读取 React 事件回调
    const elementProps = targetElement[elementPropsKey];
    if (elementProps) {
      const callbackNameList = getEventCallbackNameFromEventType(eventType);
      // click → ['onClickCapture', 'onClick']
      if (callbackNameList) {
        callbackNameList.forEach((callbackName, i) => {
          const eventCallback = elementProps[callbackName];
          if (eventCallback) {
            if (i === 0) {
              // capture 阶段：unshift（倒序插入，保证从外到内）
              paths.capture.unshift(eventCallback);
            } else {
              // bubble 阶段：push（正序插入，保证从内到外）
              paths.bubble.push(eventCallback);
            }
          }
        });
      }
    }
    targetElement = targetElement.parentNode as DOMElement;
  }
  return paths;
}

5.3 合成事件的核心：覆盖 stopPropagation

你实现的 createSyntheticEvent 覆盖了浏览器原生的 stopPropagation， 增加了一个内部的 __stopPropagation 标记。这样一来，React 可以自行控制 事件是否继续遍历捕获/冒泡链： 

function createSyntheticEvent(e: Event) {
  const syntheticEvent = e as SyntheticEvent;
  syntheticEvent.__stopPropagation = false;
  const originStopPropagation = e.stopPropagation;

  syntheticEvent.stopPropagation = () => {
    syntheticEvent.__stopPropagation = true;   // React 内部标记
    if (originStopPropagation) {
      originStopPropagation();                  // 也调用原生的
    }
  };
  return syntheticEvent;
}
🔑 为什么需要自己的标记？
因为 React 是通过 collectPaths 沿着Fiber 树（通过 DOM 桥接）收集回调的，而不是依赖浏览器的事件冒泡链。当用户调用 e.stopPropagation() 后，浏览器会阻止原生事件继续冒泡，但 React 自己的 triggerEventFlow 循环不知道这件事。所以需要在合成事件上打一个自己的标记，这样 triggerEventFlow 在遍历回调时能读到这个标记并停下来。

5.4 调度优先级映射

这是你的合成事件中最有 React 18 特色的部分——根据事件类型披上不同的 Scheduler 优先级：

function eventTypeToSchdulerPriority(eventType: string) {
  switch (eventType) {
    case 'click':
    case 'keydown':
    case 'keyup':
      return unstable_ImmediatePriority;    // 离散事件，最高优先级
    case 'scroll':
      return unstable_UserBlockingPriority; // 持续事件，中优先级
    default:
      return unstable_NormalPriority;       // 普通事件
  }
}

function triggerEventFlow(paths, se) {
  for (let i = 0; i < paths.length; i++) {
    unstable_runWithPriority(eventTypeToSchdulerPriority(se.type), () => {
      callback.call(null, se);
    });
    if (se.__stopPropagation) break;
  }
}
事件类型Scheduler 优先级场景
click / keydownImmediatePriority用户点击、按键——期望立刻响应
scrollUserBlockingPriority页面滚动——需要跟手感
其他事件NormalPriority普通交互

这是 React 18 并发模式的重要基础：用户点击后的 setState 自动获得最高优先级，不会被低优先级的渲染任务阻塞。

面试中的常见真题

Q1：事件捕获和冒泡的执行顺序是什么？

答：捕获先于冒泡，目标阶段的监听器按注册顺序执行。口诀："祖先向下捕获，到达目标执行，再从子向上冒泡"。

Q2：React 为什么要用自己的合成事件？

答：三个核心目的——

  1. 事件委托（性能）：只在容器上绑定一个监听器，而非每个元素都绑
  2. 跨浏览器一致性：抹平不同浏览器的行为差异
  3. 调度优先级（React 18）：根据事件类型（click vs scroll）匹配不同的 Scheduler 优先级，支撑并发渲染

Q3：e.target 和 e.currentTarget 的区别？

e.target：触发事件的源元素（最深层的子元素）
e.currentTarget：当前监听器绑定的元素（在事件委托中，就是 this / addEventListener 绑定的那个元素）

Q4：事件委托中如何判断 target 是某个元素？

// 方法1：tagName
if (e.target.tagName === 'LI') { /* ... */ }

// 方法2：closest（向上匹配选中的祖先）
const li = e.target.closest('li');
if (li) { /* ... */ }

// 方法3：matches
if (e.target.matches('.my-class')) { /* ... */ }

交互测验 —— 自检理解程度

问题 1

点击页面最内层的 button 后，以下代码的输出顺序是什么？

// HTML: div#a > div#b > button#c
a.addEventListener('click', () => console.log(1), true);
b.addEventListener('click', () => console.log(2), true);
c.addEventListener('click', () => console.log(3), true);
b.addEventListener('click', () => console.log(4));
a.addEventListener('click', () => console.log(5));
答案：A（1 2 3 4 5）
解析：a(true) → b(true) 是捕获阶段，先执行。到达 c(target) 阶段，按注册顺序执行 c(true)。然后冒泡：b(false) → a(false)。第一个 a 用的是 true(捕获)，最后一个 a 用的是 false(冒泡)，所以顺序是 1 2 3 4 5。

问题 2

React 合成事件中，collectPaths 的捕获回调为什么用 unshift 而冒泡用 push？

答案：B
解析：collectPaths 是从 target 向上遍历，先遇到内层元素后遇到外层元素。
- 捕获需要从外到内（外层先执行），但遍历是从内到外，所以用 unshift 把后遇到的外层回调插在前面
- 冒泡需要从内到外（内层先执行），恰好和遍历方向一致，直接用 push

问题 3

在你的 SyntheticEvent.ts 中，__stopPropagation 标记被检查了几次？分别在哪些位置？

答案：B（2 次）
解析：
1. triggerEventFlow 的 for 循环中（L93）：每次迭代检查，提前 break 终止同阶段的剩余回调
2. dispatchEvent 中（L80）：捕获阶段执行完后检查，决定是否跳过整个冒泡阶段
这两个检查分别对应"阶段内中断"和"阶段间中断"。

问题 4（实战）

以下代码，如果你点击了 li 元素，控制台会输出什么？

const ul = document.querySelector('ul');
ul.addEventListener('click', (e) => {
  console.log('ul 捕获', e.eventPhase);
}, true);
ul.addEventListener('click', (e) => {
  console.log('ul 冒泡', e.eventPhase);
}, false);

// 点击 li 后：
答案：B
解析：eventPhase 的值：1=CAPTURING_PHASE, 2=AT_TARGET, 3=BUBBLING_PHASE。
点击 li 后，事件先经过 ul 的捕获阶段（phase=1），因为在 ul 上注册了捕获监听器，所以触发它输出 "ul 捕获 1"。
然后到达 li（target），最后冒泡回到 ul，触发冒泡监听器，输出 "ul 冒泡 3"。
注意：因为监听器绑在 ul 上而非 li 上，所以 eventPhase 始终是 1 或 3（不会是 2）。
